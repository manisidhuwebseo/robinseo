Google Publishes New Google-Agent Access Guidance: What Website Owners Should Check

Google's new technical guide explains how site owners can identify and allow verified Google-Agent requests through CDNs, firewalls and bot-detection systems.

By Robin SEONovember 19, 2026GOOGLE CRAWLING & AI AGENTS

Google has published new technical guidance for website owners who want to allow requests from Google-Agent, the user agent used by agents hosted on Google infrastructure to navigate websites and perform actions when a user requests them. The guidance appeared in Google's crawling documentation changelog on November 17, 2026.

The update is relevant to site owners who use a content delivery network (CDN), web application firewall (WAF) or bot-detection service that may challenge or block automated requests. It is not an announcement of a new Googlebot ranking system, and allowing Google-Agent is not described as a search ranking factor.

What Google-Agent is—and what it is not

Google describes Google-Agent as the name used by agents hosted on Google infrastructure to navigate the web and perform actions upon user request. That makes it different in purpose from Googlebot, which crawls pages for Google's search index. A user-triggered agent may need to move through a website, open details or interact with a supported journey rather than simply fetch a page for indexing.

Website owners should avoid treating every Google user agent as interchangeable. The correct handling depends on which Google service is making the request and what the site owner wants to permit. Google's new guide focuses on recognising and allowing Google-Agent traffic through security layers—not on changing how a page is indexed or ranked.

What changed in Google's documentation?

The Google Crawling Infrastructure changelog lists a November 17 update titled “Added guidance on allowing Google-Agent.” The guide explains how to prevent legitimate requests from being blocked by a CDN, firewall or bot-detection service while keeping existing security controls in place.

Google says each Google-Agent request includes a User-Agent header containing Google-Agent and originates from an IP address listed in Google's user-triggered-agents JSON file. Google also says it is experimenting with Web Bot Auth for this agent identity. Participating requests may include a Signature-Agent value identifying https://agent.bot.goog, together with signature headers.

How to verify a request

Google recommends using more than a user-agent string alone. A practical process is:

  1. Check the request header. Confirm that the user-agent contains Google-Agent.
  2. Verify the source IP. Compare the request address with Google's published user-triggered agent IP ranges and keep the source list current.
  3. Validate signed requests when available. If Web Bot Auth headers are present, verify the signature and Signature-Agent identity using Google's documented process.
  4. Apply a narrow allow rule. Permit only requests that pass your security policy. Do not create a broad allow rule for every bot or every data-centre request.
  5. Keep a record. Log the decision and review the rule when your CDN, WAF or bot-management provider changes its configuration.

Google links to the current user-triggered agents reference and the Web Bot Auth public key directory. Follow current documentation rather than copying an IP list into a rule and leaving it unchanged indefinitely.

Check rule priority and interactive challenges

A narrow allow rule may still fail if a broader security rule runs first. Google advises checking that the verified Google-Agent rule has higher priority than general data-centre ASN blocks, managed bot rules or AI-agent category policies that could override it.

Also review interactive challenges. A firewall may return a page successfully but then display a CAPTCHA or JavaScript challenge when the agent clicks a button or submits a form. Google's guide says verified requests may need those challenges skipped as well as basic HTTP blocks. This should apply only to traffic that has passed your verification checks.

Test the whole journey, not just the homepage

Allowing the initial page load may not be enough for a user-requested task. Google's troubleshooting guidance calls out on-site search, filters, detail pages, add-to-cart, booking and underlying XHR, GraphQL or api.* endpoints. If the site is intended to support an action, the relevant page and API requests need to be considered together.

Review shared-IP rate limits as well. Google notes that multiple users' requests may share an egress pool, so a simple per-IP threshold could block legitimate activity when requests arrive concurrently. Your security team should decide whether a verified agent range needs a carefully scoped rate-limit exception.

Preserve headers through proxies and load balancers

Some websites sit behind several layers: a CDN, WAF, reverse proxy, load balancer and application server. If those layers strip or replace the original client IP or request headers, the final security decision may not have enough information to verify the agent.

Google recommends preserving the original client IP and user-agent, along with Signature, Signature-Input and Signature-Agent headers for signed requests. Ask your hosting or security provider how it passes these values between layers and where verification should occur.

Should every business website allow Google-Agent?

Not automatically. The right decision depends on whether the business wants user-triggered Google agents to interact with its public website and whether the site can verify requests safely. A brochure website may have little interactive functionality. An ecommerce store, service marketplace or appointment website may have more complex journeys and additional privacy, fraud and transaction controls.

Do not weaken security simply because a request claims to be an AI agent. Do not allow traffic based on the user-agent string alone, and do not exempt an entire network range without verifying it against Google's current documentation. Keep authentication, payment checks, permissions, consent and anti-abuse controls in place.

What this means for SEO and technical teams

The immediate task is a technical access review, not a content rewrite. SEO teams can coordinate with developers and security teams to identify whether legitimate user-triggered requests are being blocked. They should not promise that allowing Google-Agent will improve rankings, indexing, AI citations or traffic; Google's guide makes no such claim.

Document CDN and WAF rules, identify bot challenges on key journeys, verify request logs, check proxy header handling and test any narrow exception in a controlled environment. Re-test after security changes. If a third-party provider manages the firewall, ask how Google-Agent verification is implemented.

Frequently asked questions

Is Google-Agent the same as Googlebot?

No. Google describes Google-Agent as an agent hosted on Google infrastructure that navigates websites and performs actions when a user requests them. Googlebot is used for crawling content for Search. Their purposes and handling should not be assumed identical.

Does allowing Google-Agent improve rankings?

Google's new guide is about allowing verified user-triggered agent traffic through security systems. It does not say that allowing the agent improves rankings, indexing or search visibility.

Is checking the user-agent string enough?

No. Google recommends confirming the source IP against its published user-triggered agent ranges and validating Web Bot Auth signatures when present. A user-agent string by itself can be spoofed.

Should Google-Agent bypass every CAPTCHA or firewall rule?

No. Only requests that pass your verification policy should receive a narrowly scoped exception. Preserve other security controls and review which actions and endpoints are covered.

Does this require a robots.txt change?

The new guide focuses on CDN, firewall and bot-detection handling. It does not instruct site owners to add a robots.txt rule. Review the relevant Google documentation and your own access policy before making changes.
